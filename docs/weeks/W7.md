# Week 7 — Adaptive Scrutiny and bounded specialists

Spec section 6, week 7:

> **Adaptive Scrutiny** + bounded specialists — she works overnight, reports at breakfast

Spec section 4 is the design. ADR-0002 and ADR-0003 are the decisions. `scrutiny/policy.py`
is already written and tested; this week finishes the layer around it.

## Goal

The decision layer no other project ships. Seven axes, five actions, a threshold table, and a
dispatch switch — the thing that decides what is worth acting on before an expensive model is
invoked.

Spec section 4 on why this matters more than it sounds:

> scoring rejects low-value signals **before the expensive model is invoked**. That's the
> difference between an assistant that pings you forty times a day and one you trust.

It is week 7 and not week 1 because two of the seven axes are meaningless earlier. `novelty`
is measured against the vault, which was empty until week 3. `specificity` asks how
completely an action is determined, which cannot be judged without the tool surface that
would execute it — week 5.

## Done when

1. `scrutiny/score.py` produces seven valid axes from a signal, on `fast`, with no tools.
2. `scrutiny.policy.load_table()` loads and validates `config/scrutiny.yaml` at startup, and
   fails loudly on a malformed table rather than at 3am on the one signal that reaches it.
3. Every decision in `scrutiny.db` names the rule that produced it. Zero rows with an empty
   rule.
4. All five actions have fired against real signals. Especially `propagate` — if it has never
   fired, you have built four actions (ADR-0002).
5. `high_risk_always_asks` has fired on a signal where every other axis argued for acting.
6. The scored path costs materially less than the unscored path, and you have the number.
7. A bounded specialist ran overnight, stayed inside its budget, produced a branch, and
   reported at breakfast.
8. Corrections are being logged with the scores and the rule, not just the corrected action.
9. `make eval` still passes and `known-good` advances.

## Prerequisites

- W6 complete. Modes working, corrections ledger populated, eval green.
- W5's supervisor running and **proven**: you have watched a budget kill, and watched a
  revert. This week is the first time she runs while you are asleep, and the supervisor is
  the only thing standing between a bug and a 2M-token night.
- A populated vault. `novelty` against a thin vault scores everything as new and every signal
  reaches the expensive path, which is precisely the failure this layer exists to prevent.

## Steps

### 1. The scorer

`scrutiny/score.py`. The contract is already written into the docstrings; implement to it.

Two properties of the `scorer` entry in `config/agents.yaml`, both load-bearing:

- **`model: fast`.** Spec section 4: "the 4B router does the scoring." Scoring on `daily`
  makes triage cost more than skipping triage and deletes the entire economic argument for
  the layer.
- **`tools: []`.** This is the one place ingested text meets a model. Instructions hidden in
  an email have nothing to call. ADR-0006, and it is the narrow point the whole security
  model rests on.

```bash
uv run python -m scrutiny.score --text "Can you look at the invoice from Tuesday" --json
```

Six floats in 0.0-1.0 and one boolean. `conflict` is a boolean because a signal either
contradicts something already recorded or it does not; a 0.4 conflict is not a thing.

The scorer **never returns, suggests, or names an action.** If a prompt change makes the
model emit an action, that is a bug even when the action is right — the model producing seven
numbers and Python producing the decision is the entire separation, and a model that names
actions has an injection surface that a model producing numbers does not.

`parse_score` is strict. A missing axis, an extra axis, a value out of range, or unparseable
JSON all raise. A repaired score is a guess wearing a number, and the threshold table cannot
tell the difference between a real 0.8 and a defaulted one.

`novelty` needs a retrieval lookup against the vault, precomputed by the caller and passed in
as `context` — read-only, and outside the scorer so the scorer stays a pure text-to-numbers
call.

```bash
uv run pytest tests/test_score.py -q
```

### 2. Finish the table loader

`scrutiny.policy.load_table` is the last `NotImplementedError` in the module. Validation is
not optional and is not deferred to first use:

- every rule has a name, a `when` and an action that is one of the five
- rule names are unique, since decisions are keyed on them
- every `when` parses under the restricted grammar in `policy.evaluate`
- a `floor` rule exists

```bash
uv run python -c "from scrutiny.policy import load_table; t = load_table(); print(len(t.rules), 'rules'); print(t.rule('floor').action)"
uv run pytest tests/test_policy.py -q
```

The existing suite is 45 passed and 1 xfailed against a table built in-process. Adding
`load_table` should turn the xfail green and change nothing else. If a dispatch test breaks
when the real table loads, the shipped table and the test table disagree, and the shipped
table is the one that matters.

Parsing every `when` at startup is the point of validating early. A typo in a rule expression
that fails at load is an annoyance; the same typo failing at 3am on the one signal that
reaches that rule is an outage you diagnose from a journal.

### 3. The daemon

`scrutiny/daemon.py`. It consumes signals and produces decisions, and it does nothing else.

```
signal  ->  precompute novelty context (retrieval, read-only)
        ->  score  (fast, tools: [], the only model call)
        ->  decide (pure Python, the table, no model)
        ->  dispatch
        ->  record: signal id, seven scores, rule name, action, timestamp
```

Spec section 4 lists the four signal types: a message, a calendar change, an observed
pattern, and the end of a brainstorm session. That last one is the W6 join — a brainstorm
note leaves W6's consolidation and enters here as a signal, which is how a brainstorm
produces follow-up without her interrupting the brainstorm to produce it.

```bash
uv run python -m scrutiny.daemon --once --dry-run | head -40
sudo systemctl enable --now friday-scrutiny.service
journalctl -fu friday-scrutiny.service
```

Dispatch, per action, from `config/scrutiny.yaml`:

| Action | Where it goes |
|---|---|
| `act` | Execute within the calling agent's allowlist, then report. Never outside it |
| `ask` | The inbox. It stays there. `ask_expires: false` and there is no key that changes it |
| `watch` | Re-scored on a related signal or after `watch_reevaluate_after_hours: 72`, dropped at `watch_max_age_days: 14` |
| `ignore` | Logged and dropped. Logged, because the ignore rate is a health metric |
| `propagate` | `propagate_to: researcher`, with that agent's budget, allowlist and branch |

`ask_expires: false` deserves restating because it is the kind of thing that gets added later
as a convenience: there is no timeout that converts an ask into an action. A system that acts
because you did not answer in time is not bounded, it is delayed-unbounded.

A `watch` re-evaluation is a **fresh score**, not a reuse of the old one. The reason a signal
was watched is usually that information was missing, and reusing the score guarantees the
same outcome forever.

### 4. Bounded specialists

`propagate` hands work to a specialist with its own budget, allowlist and branch. That is the
whole difference from `act`, and ADR-0002 says collapsing them is the mistake to avoid.

`researcher` in `config/agents.yaml`: `daily`, tools `[search, fs_read, memory_read,
mail_read]`, 150k tokens, 3600s wall clock, `can_write: false`. The largest read-only budget
in the system, and it cannot write.

```bash
uv run python -m friday.tools.serve --agent researcher --list
uv run python -m scrutiny.daemon --propagate-test "work out whether the roof quote from March is still competitive"
```

The specialist reports back through `ask`. It does not act on its findings, because it was
handed an undetermined task — that is what `specificity < specificity_low` meant when the
rule fired.

Budgets are enforced by the supervisor, not by the specialist. A budget the budgeted process
enforces on itself is a suggestion (spec section 9, W5 step 8).

### 5. The first overnight run

Spec section 10:

> **Runaway overnight tasks.** Your first unbounded run will burn 2M tokens for nothing.

It says "will", not "may". Before you sleep on it:

```bash
# The aggregate ceilings above the per-task ones. config/friday.toml [budgets].
grep -A6 '^\[budgets\]' config/friday.toml

# The supervisor is up and has been proven, not just started.
systemctl is-active friday-supervisor.service
journalctl -u friday-supervisor.service --since '7 days ago' | grep -c 'budget kill'

# The kill switch works from your phone, tonight, before you need it.
uv run python -m supervisor.killswitch --test
```

Then run one task. One.

```bash
uv run python -m scrutiny.daemon --overnight --max-tasks 1
```

In the morning, read the report before the branch and the branch before the diff:

```bash
uv run python -m friday.cli inbox
sudo -u friday git -C /srv/friday/work log --oneline --since=midnight
sudo -u friday git -C /srv/friday/work diff known-good..HEAD --stat
sqlite3 /srv/friday/db/scrutiny.db \
  "select action, rule, count(*) from decisions where ts > date('now','-1 day') group by 1,2 order by 3 desc;"
```

Branch only, human merge. Spec section 9: not once, not for small things.

### 6. Corrections and the accuracy report

Spec section 10: "Log every correction from day one — that's your fine-tuning set." Day one
of this layer is today.

`config/scrutiny.yaml` specifies what a correction contains and why: the decision id, the
rule that fired, the seven scores, the action taken and the action you wanted. Recording only
the new action teaches nothing — the useful signal is which **rule** was wrong on which
**scores**.

```bash
uv run python -m scrutiny.corrections --last --to ignore --note "this was me complaining"
uv run python -m scrutiny.corrections --report --since '14 days ago'
```

The report is per-rule, and there are two shapes to read it for:

**Which rule is wrong.** A rule with a high correction rate is either mis-scoped or reading
an axis that is being scored badly. Fix the rule or fix the scorer prompt; do not add a rule
in front of it to catch the exception, or the table stops being readable in one sitting.

**The `floor` rate.** `floor` is an explicit rule so that it shows up in the accuracy report
like any other. A `floor` rate that climbs means the table has a gap — signals are arriving
that nothing above describes.

Then tune the thresholds. Against real corrections, not intuition. Change one at a time and
re-run the report over the same window; two threshold changes at once and you cannot
attribute the difference.

**The ratchet.** ADR-0013: a correction that keeps recurring becomes a permanent rule.

```bash
uv run python -m scrutiny.ratchet --propose --since '14 days ago'
```

It emits a **diff against `config/scrutiny.yaml` and never applies it.** ADR-0002 holds — the
threshold table is written and maintained by hand, and that is exactly what makes it
correctable in a way a model choosing actions freeform is not. The ratchet does the tedious
part: which rule was wrong, on which scores, how many times. You read the diff and merge it.

A ratchet that auto-applied would be a system rewriting its own policy unattended, which is
the same thing `auto_apply_proposals: false` refuses for the profile and `can_write: false`
refuses for the Curator, for the same reason.

### 7. Prove the economics

Done-when 6 is a number, and it is the claim the whole layer rests on.

```bash
uv run python -m scrutiny.report --cost --since '7 days ago'
```

What it must show: total signals, the fraction rejected at `ignore` and `watch` before any
expensive call, tokens spent on scoring, and tokens that would have been spent had every
signal gone to `daily`.

If scoring costs more than it saves, something is wired wrong — usually the scorer running on
`daily`, or novelty scoring near 1.0 for everything because the vault lookup is not actually
being consulted.

## Failure modes

**`propagate` never fires.** The most likely way ADR-0002 gets violated in practice: the
action exists in the table and nothing ever reaches it, so you effectively have four actions.
Check the rule — `important_but_undetermined_propagates` needs `specificity < 0.40` and
`impact >= 0.60` together, and if the scorer never emits low specificity, the scorer prompt
is the problem, not the rule.

**Everything is `ignore`.** Usually `novelty` scoring near zero because the vault lookup
matches too loosely, so every signal looks like something already recorded. Check the novelty
context before the thresholds.

**Everything is `watch`.** `confidence` is scoring low across the board. A 4B model asked to
rate its own confidence on a vague prompt returns 0.4 for everything. Sharpen the prompt, or
give it examples; do not lower `confidence_low`, which turns "unsure" into "act".

**She acted on something she should have asked about.** Read the rule that fired, not the
score. Nine times in ten the rule is right and the score was wrong, and the fix is the scorer
prompt. If the rule really is wrong, fix it in place — do not add a rule in front of it.

**A rule was added at the top to catch one bad case.** The table stops being readable in one
sitting, which is the property that makes this layer auditable. Fix the rule that was wrong.

**The scorer starts emitting actions.** A prompt change asked it to "decide" instead of
"score". Even when the actions are right, this is a bug: the boundary is that the model
produces numbers and Python produces decisions.

**Scoring runs on `daily` "for quality".** The layer now costs more than it saves. Spec
section 4 and ADR-0002 both specify `fast`.

**The overnight run burned the budget.** Predicted in spec section 10. Check that the
supervisor killed it rather than that it stopped on its own — a task that stopped on its own
tells you nothing about whether the budget works.

**Thresholds tuned before any corrections exist.** Tuning against intuition produces a table
that matches your idea of your own priorities rather than your actual ones. Corrections
first, thresholds second.

## Do not do yet

- **No skill optimisation.** W8, and it depends on the corrections ledger you started
  filling this week.
- **Do not raise `--max-tasks` past 1** until a full week of single-task overnight runs has
  gone cleanly.
- **Do not give a specialist write access** because it would be more useful. `researcher` is
  `can_write: false` deliberately — it is the largest budget in the system and the one most
  exposed to untrusted input.
- **Do not add an eighth axis.** ADR-0002: a schema change touching the scorer, the table and
  the tests, and it needs an ADR. Most things that feel like a new axis are a rule.
- **Do not add a sixth action.** Same.
- **Do not add an `ask` timeout.** Not as a convenience, not as an option. `ask_expires:
  false` is a boundary.
- **Do not merge an agent branch unread.**
