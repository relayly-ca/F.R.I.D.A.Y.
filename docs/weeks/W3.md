# Week 3 — memory, retrieval, the eval gate, and the loops that fill the vault

Spec section 6, the 2-3 row and the week-3 row:

> Memory: vault, Qdrant, FTS5, reranker, **eval set** — 20/25 on your own eval questions
> OpenJarvis `monitor_operative` + `morning_digest` — vault grows without you writing in it

## Goal

This is the long pole. Everything before it was installation; everything after it depends on
it working. Spec section 6: "Week 2-3 is the least exciting and the most load-bearing."

Four things: build the index, build the retrieval pipeline exactly as spec section 7
describes it, get to 20/25, and then turn on the two loops that make the vault grow without
you writing in it.

The consolidation loop is where ADR-0007 lives, and it is the decision most likely to be
quietly reverted by someone implementing it. **Bounded memory means consolidate when full.**
The write path blocks. It is not a nightly compression job, and building it as one produces
something that works for six weeks and then degrades on a curve nobody is watching.

## Done when

1. `make eval` scores 20 or better out of 25 on `eval/questions.yaml`.
2. The score is reproducible: run it three times and it does not move by more than a point.
3. Qdrant holds the vault and the episodic log; FTS5 holds the same corpus; a query hits both.
4. Retrieval is exactly spec section 7's pipeline, in that order, with the reranker on top.
5. Every retrieved chunk carries its source and timestamp into the prompt, and she qualifies
   an answer older than `stale_after_days`.
6. Filling memory past `max_live_events` blocks the write until consolidation completes, and
   you have watched it happen.
7. `morning_digest` wrote a daily note you did not write, and it is accurate.
8. `monitor_operative` has been running for 48 hours and the vault has grown from it.
9. `make known-good` succeeds, tagging the first known-good commit.

## Prerequisites

- W2 complete. `eval/questions.yaml` written **before** this week, not during it.
- `sources.db` holding at least a few weeks of calendar and Matrix history. Retrieval tuned
  against 200 rows tells you nothing about retrieval at 10,000.
- `embed` and `rerank` up on 8082 and 8085, from W1.
- `vault/profile.md` written by hand.

## Steps

### 1. Qdrant

```bash
sudo install -d -m 0750 -o friday -g friday /srv/friday/db/qdrant
sudo docker run -d --name friday-qdrant --restart unless-stopped \
  -p 127.0.0.1:6333:6333 \
  -v /srv/friday/db/qdrant:/qdrant/storage \
  qdrant/qdrant:latest
curl -s http://127.0.0.1:6333/readyz
```

`-p 127.0.0.1:6333:6333` and not `-p 6333:6333`. Docker's default publish binds every
interface and, worse, writes an iptables rule that a host firewall does not filter. Preflight
catches it; the container is easier to fix than the afternoon spent wondering why.

Re-running the `docker run` above fails with a name conflict rather than doing nothing, which
is not idempotent. `install/06-qdrant.sh` wraps it properly; by hand, guard it:

```bash
sudo docker ps -a --filter name=^friday-qdrant$ --format '{{.Names}}' | grep -q . \
  || sudo docker run -d --name friday-qdrant ... # as above
```

Create the collection. `embed_dim: 1024` from `config/memory.yaml` is bge-m3's dimension, and
changing the embedding model later invalidates every vector in here — it is not a
re-embedding, it is a rebuild.

```bash
uv run python -m friday.memory.index --create-collection
curl -s http://127.0.0.1:6333/collections/friday | jq '.result.config.params.vectors'
```

### 2. The episodic log and FTS5

Tier 2. Append-only, never edited, only compressed. `config/memory.yaml` says
`append_only: true` and that is an API property, not a comment: no `UPDATE` and no `DELETE`
in the public interface. Compression rewrites into summary rows and archives the originals to
`db/archive/`; it does not edit in place.

```bash
uv run python -m friday.memory.episodic --init
sqlite3 /srv/friday/db/episodic.db '.schema'
sqlite3 /srv/friday/db/episodic.db 'pragma journal_mode;'   # must print wal
```

FTS5 lives in the same file (`config/memory.yaml`, `fts_db`). One file, one backup, one
consistent snapshot. An external content table over the episodic rows, with triggers, so the
index cannot drift from the log.

```bash
sqlite3 /srv/friday/db/episodic.db "select count(*) from episodic;"
sqlite3 /srv/friday/db/episodic.db "select count(*) from episodic_fts;"
```

Those two numbers must match. If they diverge, the triggers are wrong and keyword retrieval
is silently returning a subset.

### 3. Backfill from sources.db

`sources.db` is a landing zone; the episodic log is the durable record.

```bash
uv run python -m friday.memory.ingest --from-sources --since 2000-01-01 --dry-run
uv run python -m friday.memory.ingest --from-sources --since 2000-01-01
```

Chunking is `chunk_tokens: 512` with `chunk_overlap_tokens: 64`. Chunk on structure first —
a calendar event, a message, a note section — and only fall back to a token window when a
unit exceeds the budget. A message split down the middle retrieves as two halves that each
make less sense than the whole.

Embed and upsert:

```bash
uv run python -m friday.memory.index --reindex
curl -s http://127.0.0.1:6333/collections/friday | jq '.result.points_count'
```

Provenance travels with the chunk into Qdrant's payload and into the FTS row: source,
external id, occurred_at, sensitivity. `carry_provenance: true` in `config/memory.yaml`. It
is not decoration — spec section 7 is explicit that it is how she says "you told me this in
March, it may be stale," and it is how you find the source of a wrong answer.

### 4. Retrieval

Spec section 7, verbatim, and the order is not negotiable:

> expand query → parallel keyword + vector (top 30 each) → dedupe → rerank to top 8 → recency boost

`friday/memory/retrieve.py`. Each step, and why it is where it is:

**Expand** to `expansions: 3`. Runs on `fast`. Your phrasing and the corpus's phrasing rarely
match, and this is the cheapest fix available.

**Parallel keyword and vector, 30 each.** Concurrently, not in sequence — they are
independent and the latency budget in week 5 will not survive them being serial. Keyword
catches exact names and identifiers that embeddings smear; vector catches paraphrase.

**Dedupe, then fuse with RRF.** `fusion: rrf` in `config/memory.yaml`, not score averaging.
The two systems produce scores on incomparable scales, and normalising them is a knob that
drifts silently as the corpus changes.

**Rerank to 8** with `bge-reranker-v2-m3`. This is the step that saves you at 10k documents
(spec section 10), which is why it is in week 3 and not week 8. Drop anything below
`min_rerank_score: 0.15` even if the context window has room. Padding the context to use the
budget is exactly how retrieval degrades invisibly.

**Recency boost after reranking**, `recency_half_life_days: 30`. Before reranking, a recent
irrelevant document outranks an old exact answer.

Then, unconditionally injected and not retrieved: the current date and time, today's
calendar, and `profile.md`. Retrieval can miss. These cannot be allowed to.

Sensitivity filtering goes **inside** the retrieval query, not after ranking. ADR-0008:
filtering after ranking means the ranking was computed over rows the caller may not see,
which leaks their existence through result counts and gaps.

```bash
uv run python -m friday.memory.retrieve --query "what did I say about the roof" --explain
```

`--explain` should print each stage's survivors with scores. Build it now; in week 4 it is
the only tool that tells you which new source broke the eval.

### 5. The eval harness

```bash
uv run python eval/run_eval.py --questions eval/questions.yaml
make eval
```

It must be runnable non-interactively as the supervisor's user (ADR-0009), because in week 5
it becomes part of the rollback mechanism and not just a development tool. No prompts, no
TTY assumptions, exit code 0 on pass, non-zero on fail, and a machine-readable result in
`eval/results/`.

Now iterate. Expect the first run somewhere between 8 and 14. The order to work in, because
it goes from cheapest to most expensive:

1. **Read the failures individually with `--explain`.** Half of them are ingestion, not
   retrieval: the answer is not in the corpus at all. Fix those first and do not touch a
   retrieval parameter.
2. **Chunking.** More failures come from bad chunk boundaries than from bad ranking.
3. **Expansion.** Cheap and often worth two points.
4. **`min_rerank_score` and `rerank_to`.** Last, and in small steps.

Record each run. A score that moves without you knowing which change moved it is not a
measurement.

```bash
ls -1 eval/results/ | tail -5
```

**Do not tune the questions.** The moment you soften a question to make it pass, the set
stops being a gate and becomes a scoreboard. If a question is genuinely unanswerable from
any source, replace it with a different question, and note why in the file.

Run it three times when you hit 20. A score that moves two points between identical runs
means something in the pipeline is nondeterministic — usually a temperature above zero
somewhere it should not be, or a concurrent index write.

### 6. The vault and the consolidation loop

Tier 3. `daily/ projects/ people/ ideas/`, written by the consolidation loop, editable by
you, git-backed with one commit per run (`commit_per_run: true`) — per-note commits break the
revert the supervisor depends on in week 5.

Now the part that matters. **ADR-0007: bounded memory means consolidate when full.**

```
write() →  live_events >= max_live_events?
             yes → BLOCK. Run consolidation. Then write.
             no  → live_events >= soft_start_at * max?
                     yes → kick off consolidation in the background, write now
                     no  → write now
```

The block is the design. It is the forcing function that makes her curate rather than hoard.
The tempting softening — queue the write and drain it later — is not a softening, it is
unbounded memory in a different file, and ADR-0007 rules it out by name.

`max_live_events: 8000` and `max_vault_notes: 2000` from `config/memory.yaml`. Both are below
the ~10k document mark where spec section 10 says retrieval collapses. That is where the
numbers came from; tune them against the eval set, not against how full the disk is.

```bash
uv run python -m friday.memory.consolidate --once --dry-run
uv run python -m friday.memory.consolidate --once
sudo -u friday git -C /srv/friday/vault log --oneline -3
```

Then prove the block. This is Done-when 6 and it is the one people skip:

```bash
uv run python -m friday.memory.consolidate --simulate-full
# Expect: the write path blocks, consolidation runs, the write completes afterwards.
# Expect NOT: the write succeeds immediately, or is queued, or is dropped.
```

`scheduled_pass: "03:00"` is allowed and is not the mechanism. ADR-0007 permits a scheduled
pass in addition; it forbids it being the only consolidation.

### 7. The loops

Spec section 6, week 3: `monitor_operative` and `morning_digest`. The done-when is "vault
grows without you writing in it."

```bash
jarvis skill enable morning_digest      # VERIFY: against OpenJarvis's CLI
jarvis skill enable monitor_operative
sudo systemctl enable --now friday-digest.timer
systemctl list-timers 'friday-*' --no-pager
```

`digest` runs on `daily` with `memory_read`, `calendar_read`, `vault_write`, a 32k token
ceiling and a 900s wall clock — `config/agents.yaml`, and every field of that is a hard
budget rather than a suggestion.

The digest is the first thing she writes on her own. Read the first week of them carefully.
A digest that is subtly wrong every day is worse than no digest, because it enters the vault,
gets indexed, and is retrieved as fact in week 5. Wrong entries get corrected in the vault by
hand; that is what "editable by you" is for.

### 8. The first known-good tag

```bash
make known-good
git tag -l known-good
```

ADR-0009: the tag advances only after a full eval pass. This is the first commit that can be
a rollback target, and until week 5's supervisor exists nothing consumes it — tag it anyway,
so the supervisor has somewhere to revert to on the day it is switched on.

## Failure modes

**The eval sits at 16 and every change moves it by one point in either direction.** You are
tuning noise. Stop, take the six failures, and read each one with `--explain`. Usually four
of them are the same root cause and it is chunking.

**Qdrant published on every interface.** `-p 6333:6333` instead of `-p 127.0.0.1:6333:6333`.
Docker writes the iptables rule below your firewall. Preflight fails; believe it.

**FTS5 count diverges from the episodic count.** The triggers do not cover every write path,
usually because a bulk backfill bypassed them. Keyword retrieval then silently returns a
subset and the eval drops by three points for no visible reason.

**Recency boost applied before reranking.** Everything recent wins, the eval drops on exactly
the temporal questions, and the pipeline still looks like spec section 7 at a glance. Check
the order in `retrieve.py` against section 7 before anything else.

**Consolidation deletes something you wanted.** It is git-backed with one commit per run for
this reason. `git -C /srv/friday/vault revert` and then fix the extraction schema.

**Consolidation was built as a nightly job.** The most likely way this week goes wrong,
because it is easier to implement and it passes a casual test. ADR-0007 rejects it by name.
The tell: `tests/test_consolidate.py` has no test that a write blocks. Symptoms arrive in
week 6 as slowly degrading retrieval.

**The digest is confidently wrong.** It has already been indexed. Correct the note in the
vault by hand, re-run the index, and tighten the extraction schema — do not raise the model
alias, which costs more and fixes nothing.

**Re-embedding everything after switching embedding models.** Not a re-embed, a rebuild.
`embed_dim` changes, every existing vector is meaningless, and the collection must be
recreated. Decide on bge-m3 and stay there through week 8.

## Do not do yet

- **No new sources.** Mail, files, browser and Home Assistant are week 4, and week 4's rule
  is that the eval score holds after each one. Adding them now means you cannot attribute a
  drop.
- **No voice.** Week 4 at the earliest.
- **No scrutiny.** Week 7. `novelty` is measured against the vault, and the vault has only
  just started filling.
- **No agent writes outside the vault.** `vault_write` is the only write capability that
  exists; `git` and `shell` arrive in week 5 behind a container.
- **Do not raise `max_live_events` because consolidation is slow.** That is the forcing
  function working. Fix the consolidation, or accept the bound.
- **Do not add a second embedding model** for "better recall on code" or anything else.
  ADR-0001, and two vector spaces in one collection is a rebuild.
