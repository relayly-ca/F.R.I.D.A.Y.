# Week 1 — inference, routing, agent runtime, messaging

Spec section 6, both week-1 rows:

> llama.cpp + LiteLLM + **OpenJarvis** one-line install, `--preset chat-simple` — you chat locally
> Conduit + mautrix bridges + Hermes gateway — you text FRIDAY from your phone

## Goal

Get a model answering on this box, put one endpoint in front of it, put an agent runtime on
top of that, and reach the whole thing from your phone without opening a port.

That last clause is the week's real work. "You text FRIDAY from your phone" reads like a
messaging task and is mostly a network task: spec section 9 says no port forwarding, so the
phone reaches Conduit over a mesh or it does not reach it at all. Build the mesh in week 1,
because every later phase that involves your phone — DAVx5 in week 2, the kill switch in
week 5 — assumes it is already there.

## Done when

1. `curl http://127.0.0.1:4000/v1/chat/completions` against the `daily` alias returns a
   sensible completion, using a per-agent virtual key and not the master key.
2. `daily` falls back to `fast` when you stop the `daily` llama-server, and recovers when
   you start it.
3. OpenJarvis is installed, initialised, and holds a conversation through LiteLLM.
4. You send a message from the Matrix client on your phone, over the mesh, and FRIDAY
   answers in the room.
5. At least one mautrix bridge is linked and backfilling into Conduit.
6. `make preflight` passes with no `FAIL`.
7. `/srv/friday/vault/profile.md` is written by hand and no longer contains the stub text.

## Prerequisites

- Arch Linux, current, with an NVIDIA GPU and a working driver. `nvidia-smi -L` must list a
  device before you start; nothing in this guide fixes a broken driver.
- Full-disk encryption (spec section 9). If this box is not encrypted, do that first — it is
  an install-time decision and there is no later step that adds it.
- 120 GB free under `/srv`, per preflight's default.
- A phone you are willing to install a Matrix client and a mesh client on.

`make preflight` at this point is expected to fail on: service accounts, `agent/core`, the
memory tiers, the age identity, and the venv. Everything in section 1, 2 and 3 of its output
— GPU, VRAM, disk — must already pass. Those are hardware, and this guide does not change
hardware.

## Steps

### 1. Packages

`install/00-arch-packages.sh` is this, in a script, with a `--needed` on every line so a
re-run is a no-op.

```bash
sudo pacman -Syu --needed --noconfirm \
  base-devel git cmake ninja pkgconf \
  cuda cudnn nvidia-utils \
  uv python \
  age sops \
  jq sqlite ripgrep rsync \
  docker docker-compose docker-buildx \
  iproute2 nftables wireguard-tools \
  ffmpeg \
  polkit
```

`paru` for the AUR. Bootstrap it only if it is missing, so this block is safe to re-run.

```bash
command -v paru >/dev/null || {
  tmp=$(mktemp -d) && git clone --depth 1 https://aur.archlinux.org/paru-bin.git "$tmp/paru-bin" \
    && (cd "$tmp/paru-bin" && makepkg -si --noconfirm) && rm -rf "$tmp"
}
```

llama.cpp with CUDA. Check the repositories before reaching for the AUR — this package has
moved between the two.

```bash
pacman -Ss '^llama.cpp' || true
# VERIFY: if the repositories carry a CUDA build, prefer it:
#   sudo pacman -S --needed --noconfirm llama.cpp-cuda
# Otherwise:
paru -S --needed --noconfirm llama.cpp-cuda
```

Docker runs Qdrant in week 3 and Langfuse now, and OpenHands in week 5. Enable it once.

```bash
sudo systemctl enable --now docker.service
sudo usermod -aG docker "$USER"   # log out and back in for this to take effect
```

Verify CUDA reached llama.cpp. If this prints no CUDA device, the rest of the week will run
on CPU and appear to work, slowly, which is the worst possible failure because you will not
notice it for two days.

```bash
llama-server --version
nvidia-smi --query-gpu=name,memory.total,driver_version --format=csv
```

### 2. Service accounts and the install root

Order matters: users before the tree, because the tree's ownership is the security property.

```bash
sudo bash install/01-users.sh
sudo bash install/tree.sh
```

`install/tree.sh` verifies the boundary rather than asserting it — it exits non-zero if the
`friday` user can write `agent/core/`. Spec section 9 and ADR-0004. If that check fails, stop
and fix it; do not continue with a warning.

```bash
sudo -u friday test -w /srv/friday/agent/core && echo "BROKEN" || echo "ok: core is not writable by friday"
```

### 3. Secrets

Spec section 9: capabilities, not credentials. ADR-0005: no secret enters this repository,
not even encrypted. The age identity lives under the install root, root-owned, and the agent
cannot read it.

```bash
sudo install -d -m 0700 -o root -g root /srv/friday/secrets
[[ -f /srv/friday/secrets/age.key ]] || sudo sh -c 'age-keygen -o /srv/friday/secrets/age.key'
sudo chmod 0600 /srv/friday/secrets/age.key
sudo grep -oP 'public key: \K\S+' /srv/friday/secrets/age.key
```

Put that public key into `.sops.yaml`, replacing the placeholder. It is a public key; it is
safe in git, and it is the one exception ADR-0005 names.

```bash
${EDITOR:-nano} .sops.yaml
grep -q 'age1REPLACE' .sops.yaml && echo "still a placeholder" || echo "ok"
```

Now the one secret week 1 needs: the LiteLLM master key. Spec section 8 — it exists to mint
the per-agent virtual keys and for nothing else. No service is configured with it.

```bash
sudo sh -c 'umask 077; printf "LITELLM_MASTER_KEY=sk-%s\nLITELLM_DATABASE_URL=sqlite:////srv/friday/db/litellm.db\n" \
  "$(openssl rand -hex 24)" > /tmp/litellm.env'
sudo sh -c 'SOPS_AGE_KEY_FILE=/srv/friday/secrets/age.key sops --encrypt /tmp/litellm.env > /srv/friday/secrets/litellm.env.sops'
sudo shred -u /tmp/litellm.env
sudo chmod 0600 /srv/friday/secrets/litellm.env.sops
```

### 4. Python environment

Pinned to 3.12. Arch's `python` rolls forward, and a venv tracking it breaks on an unrelated
`-Syu` — at which point every service fails to start at once, on a day you changed nothing.

```bash
uv python install 3.12
uv python pin 3.12
uv sync --extra dev
uv run python -c 'import sys; print(sys.version)'
```

`install/02-python-env.sh` does the same thing into `/srv/friday/.venv`, owned by `friday`,
which is what the systemd units use. The repo-local `.venv` above is for `make test` and
`make lint`.

### 5. Weights

Spec section 1 gives the model table and then says: **verify current picks before
downloading.** Take that seriously — model names move, quantisations get re-cut, and a repo
id that was right when this file was written may not resolve.

```bash
uv tool install "huggingface_hub[cli]"
hf auth whoami || hf auth login    # only needed for gated repos
```

| Alias | Spec section 1 pick at 24 GB | Port | Repo id |
|---|---|---|---|
| `daily` | Qwen 3.6 27B @ Q4 | 8080 | `# VERIFY:` |
| `fast` | 4B router (spec section 8 names gemma4-4b) | 8081 | `# VERIFY:` |
| `embed` | bge-m3 | 8082 | `# VERIFY:` |
| `rerank` | bge-reranker-v2-m3 | 8085 | `# VERIFY:` |

Fill the fourth column in by searching Hugging Face for the GGUF conversion, then download.
The `--needed` equivalent here is that `hf download` skips files already present, so this is

```bash
sudo install -d -m 0755 -o friday -g friday /srv/friday/models
sudo -u friday hf download <REPO_ID> <FILENAME.gguf> --local-dir /srv/friday/models
```

If your card is not 24 GB, take the row from spec section 1's table that matches it, and set
`MIN_VRAM_MB` in your environment so preflight stops arguing with you:

```bash
echo 'MIN_VRAM_MB=15000' | sudo tee /etc/friday/preflight.env
```

`install/03-models.sh` wraps this, reading the repo ids from a table at the top of the
script so there is exactly one place to correct them.

### 6. llama-server

One templated unit, one env file per alias. Adding `coder` in week 5 and `vision` in week 4
is then a new env file and nothing else.

```bash
sudo install -d -m 0755 /etc/friday/llama
sudo tee /etc/friday/llama/daily.env > /dev/null <<'EOF'
MODEL=/srv/friday/models/daily.gguf
PORT=8080
ARGS=--ctx-size 16384 --n-gpu-layers 999 --flash-attn --alias qwen36-27b
EOF
sudo tee /etc/friday/llama/fast.env > /dev/null <<'EOF'
MODEL=/srv/friday/models/fast.gguf
PORT=8081
ARGS=--ctx-size 8192 --n-gpu-layers 999 --flash-attn --alias gemma4-4b
EOF
sudo tee /etc/friday/llama/embed.env > /dev/null <<'EOF'
MODEL=/srv/friday/models/bge-m3.gguf
PORT=8082
ARGS=--embedding --pooling cls --ctx-size 8192 --n-gpu-layers 999 --alias bge-m3
EOF
sudo tee /etc/friday/llama/rerank.env > /dev/null <<'EOF'
MODEL=/srv/friday/models/bge-reranker-v2-m3.gguf
PORT=8085
ARGS=--reranking --ctx-size 8192 --n-gpu-layers 999 --alias bge-reranker-v2-m3
EOF
```

Symlink or rename your downloaded GGUFs to those paths, then install the unit. It comes from
`systemd/friday-llama@.service` in this repo; `install/04-services.sh` copies every unit and
reloads.

```bash
sudo bash install/04-services.sh
sudo systemctl enable --now friday-llama@daily friday-llama@fast friday-llama@embed friday-llama@rerank
systemctl list-units 'friday-llama@*' --no-pager
```

`# VERIFY:` the llama.cpp flags above against `llama-server --help` for the version you
installed. `--flash-attn` and `--reranking` in particular have changed spelling across
releases, and a rejected flag makes the unit fail to start with a message that scrolls past.

### 7. LiteLLM

Transport only. `config/litellm.yaml` is already written and already binds loopback.

```bash
uv tool install 'litellm[proxy]'
sudo install -d -m 0750 -o friday -g friday /srv/friday/db
sudo systemctl enable --now friday-litellm.service
curl -s http://127.0.0.1:4000/health/readiness | jq .
```

Mint the per-agent virtual keys. Spec section 8: a single shared master key across agents is
not sufficient, and Hermes shipped a hardening release specifically patching a LiteLLM
credential exposure. One key per entry in `config/agents.yaml`.

```bash
sudo bash install/05-litellm-keys.sh
sudo SOPS_AGE_KEY_FILE=/srv/friday/secrets/age.key \
  sops --decrypt /srv/friday/secrets/litellm-keys.yaml | grep -c 'key:'
```

Now the first Done-when. Use a virtual key, not the master key — if this works with the
master key and you never test a virtual one, you find out in week 5.

```bash
KEY=$(sudo SOPS_AGE_KEY_FILE=/srv/friday/secrets/age.key \
  sops --decrypt /srv/friday/secrets/litellm-keys.yaml | awk '/conversation:/{getline; print $2}')
curl -s http://127.0.0.1:4000/v1/chat/completions \
  -H "Authorization: Bearer $KEY" -H 'Content-Type: application/json' \
  -d '{"model":"daily","messages":[{"role":"user","content":"Reply with the single word: ready"}]}' \
  | jq -r '.choices[0].message.content'
```

### 9. OpenJarvis

Spec section 11 gives the install verbatim. Section 6 gives the week-1 preset.

```bash
curl -fsSL https://open-jarvis.github.io/OpenJarvis/install.sh | bash
jarvis init --preset chat-simple
```

Piping a remote script into bash is what the spec says to do and it is worth being honest

```bash
curl -fsSL https://open-jarvis.github.io/OpenJarvis/install.sh | less
```

Point it at LiteLLM rather than at a model. `# VERIFY:` the exact configuration key against
OpenJarvis's own documentation; what matters is the shape — an OpenAI-compatible base URL of
`http://127.0.0.1:4000/v1` and the virtual key for the `conversation` agent, never the
master key and never a direct llama-server port.

```bash
jarvis chat "Say hello and tell me which model you are."
```

### 10. The mesh

Spec section 9: no port forwarding, Headscale or WireGuard only. Pick one. Headscale if you
want more than two devices and coordination you do not have to think about; plain WireGuard
if you want the smallest thing that works.

```bash
# Option A: WireGuard. Smallest possible.
sudo install -d -m 0700 /etc/wireguard
[[ -f /etc/wireguard/friday.key ]] || sudo sh -c 'umask 077; wg genkey > /etc/wireguard/friday.key'
sudo sh -c 'wg pubkey < /etc/wireguard/friday.key > /etc/wireguard/friday.pub'
# Write /etc/wireguard/wg0.conf with this box and your phone as peers, then:
sudo systemctl enable --now wg-quick@wg0
```

```bash
# Option B: Headscale, if you want a coordination server.
paru -S --needed --noconfirm headscale   # VERIFY: may be in the repositories now
sudo systemctl enable --now headscale
```

Whichever you choose, the test is the same and it is not "the phone can ping the box". It is
that nothing is reachable from outside the mesh:

```bash
ss -tlnp | awk '$4 !~ /^(127\.|\[::1\])/ {print}'
```

Anything printed here that is not bound to the mesh interface is a finding. Preflight fails
on exactly this.

### 11. Conduit and the bridges

```bash
paru -S --needed --noconfirm matrix-conduit   # VERIFY: package name; conduwuit is the active fork
sudo install -d -m 0750 -o friday -g friday /srv/friday/db/conduit
```

Conduit's configuration must bind `127.0.0.1:7424`, and reverse-proxy or mesh-bind for the
phone. Federation off: this homeserver exists to hold your bridged conversations, and
federating it exposes it to the network the spec spent section 9 keeping it off.

```bash
sudo systemctl enable --now conduit.service
curl -s http://127.0.0.1:7424/_matrix/client/versions | jq -r '.versions[-1]'
```

Register two accounts: yours, and `friday`. Then install one bridge. **One.** Spec section
10 names bridge instability as the first thing that breaks, WhatsApp especially, and
debugging two unfamiliar bridges at once is how a week-1 evening becomes a week-1 weekend.

```bash
paru -S --needed --noconfirm mautrix-whatsapp   # or mautrix-signal, mautrix-telegram
sudo systemctl enable --now mautrix-whatsapp.service
```

Link it from your Matrix client by messaging the bridge bot. Bridge credentials are the
bridge's own business and do not enter this repository.

## Verification

```bash
make preflight
```

No `FAIL`. Then, in order:

```bash
# 1. Every resident model is up and answering.
for p in 8080 8081 8082 8085; do curl -sf "http://127.0.0.1:$p/health" >/dev/null \
  && echo "$p ok" || echo "$p DOWN"; done

  -H 'Content-Type: application/json' \

sudo systemctl start friday-llama@daily

# 4. Nothing off-loopback.
ss -tlnH | awk '$4 !~ /^(127\.|\[::1\])/ {print "OFF-LOOPBACK: " $4}'
```

## Failure modes

**llama-server starts but runs on CPU.** The unit is green, tokens appear, everything looks
fine, and it is thirty times too slow. `nvidia-smi` during a request shows no process. Cause
is almost always a llama.cpp build without CUDA, or `--n-gpu-layers` unset. Check
`llama-server --version` for the CUDA banner before you debug anything else.

**Model loads, then the second model does not.** Two 27B-class models do not fit in 24 GB.
The resident set is roughly 6 GB (`fast`, `embed`, `rerank`, and later whisper and Kokoro)
plus the daily driver. `coder` and `vision` are on-demand for exactly this reason, and week 5
adds the eviction logic. If you get this in week 1, you have loaded something at the wrong
quantisation.

**LiteLLM returns 401 with a key you just minted.** The key is scoped to models it was
minted for. Check the key's model list before assuming the proxy is broken.

**Fallback does not fire.** `allowed_fails: 2` in `config/litellm.yaml` means two failures
before the alias is cooled down. A single request against a stopped backend can surface the
error rather than falling back. Send three.

**The bridge links, then unlinks a week later.** Expected. Spec section 10: re-link every few
months, WhatsApp especially. Do not restructure anything in response to this; it is the
normal operating cost of a bridge.

**Conduit federates by accident.** Check the config after any package upgrade. A federating
homeserver on a machine that holds your entire life indexed is the single worst outcome
available in this week.

**Piping install.sh to bash worked, and you did not read it.** Not recoverable by a command.
Read it before the next machine.

## Do not do yet

- **No ingestion.** No calendar, no mail, no files, no Matrix history into the index. Week 2.
- **No index at all.** Qdrant is not installed this week. `make preflight` does not check for
  it until week 3.
- **No voice.** Not the microphone, not Whisper, not Kokoro, not the wake word. This is the
  temptation the spec calls out by name: voice before memory is the mistake everyone makes.
  `config/friday.toml` ships with `[voice] enabled = false`. Leave it.
- **No scrutiny.** `scrutiny/policy.py` is implemented and tested, and it is not wired to
  anything. `scrutiny/score.py` raises `NotImplementedError` and will keep doing so until
  week 7, because `novelty` against an empty vault is meaningless.
- **No supervisor.** Week 5. Nothing is autonomous yet, so there is nothing to supervise, and
  a supervisor written before the thing it supervises supervises your guesses.
- **No OpenHands.** Week 5, and it wants a sandbox that does not exist yet.
- **Do not add a second bridge** until the first has survived a week.
