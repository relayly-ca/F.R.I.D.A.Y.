# Week 8+ — skill optimisation, the Curator, and steady state

Spec section 6, the last row:

> `jarvis optimize skills --policy dspy` + Hermes Curator — her skills improve measurably,
> not just numerously

## Goal

Everything before this week added capability. This week adds *improvement*, and the entire
difficulty is in the last four words of the done-when: **measurably, not just numerously.**

A skill library that grows is trivial to build and tells you nothing. The number of skills is
not a metric, it is a symptom, and the failure mode of every skill-optimisation system is a
library of 400 skills where 380 are near-duplicates and nobody can say whether last month's
optimisation helped. Spec section 3 already made this judgement once, about OpenClaw's
13,700-skill library: the value is the library being importable, not the count.

So this week is one third optimisation and two thirds measurement, and the measurement comes
first.

## Done when

1. A per-skill success metric exists and has been collecting for at least two weeks before
   the first optimisation run.
2. `jarvis optimize skills --policy dspy` has run against a held-out set, and you can state
   the before and after numbers for each skill it touched.
3. At least one optimisation was **rejected** because it did not improve the metric. If
   nothing has ever been rejected, you are not measuring.
4. The Hermes Curator runs weekly on `fast`, and it has retired or merged at least one skill.
5. Skill count went **down** at least once, and quality did not.
6. `make eval` still passes after every optimisation run. The retrieval eval is a separate
   gate and skill changes must not move it.
7. `agent/core/` is unchanged and the supervisor confirms it. She optimised her skills and
   not the loop that runs them.
8. `known-good` advanced only after a full eval pass, as it has every week.

## Prerequisites

- W7 complete. Scrutiny running, corrections accumulating, overnight runs bounded and clean.
- **Two weeks of skill invocation data.** This is a real prerequisite and not a nicety: DSPy
  optimises against examples, and optimising against two weeks of your actual use produces
  something different from optimising against a set you wrote in an afternoon.
- The supervisor proven against `agent/core/` modification (W5, verification 7). This week is
  the week ADR-0004 stops being theoretical.

## Steps

### 1. Measurement first

Before any optimiser runs, decide what "better" means per skill and start recording it.
Optimising against a metric you invented after seeing the results is not optimisation.

Per invocation, record: skill, inputs (hashed if sensitive), outcome, tokens, wall clock,
whether it needed a correction, and whether it was retried.

```bash
uv run python -m friday.skills.metrics --init
uv run python -m friday.skills.metrics --report --since '14 days ago'
```

Four numbers per skill, and they are not interchangeable:

| Metric | What it catches |
|---|---|
| Success rate | Did it do the thing. The baseline |
| Correction rate | Did you have to fix it after. From `scrutiny.db` |
| Cost per success | Tokens and seconds. A skill that succeeds expensively is a problem |
| Invocation count | A skill invoked twice in a month is a candidate for retirement |

Correction rate is the one that matters most and the one most often left out, because it is
the only one that measures whether the output was *right* rather than whether it *completed*.
You already have the ledger — spec section 10 told you to start it on day one, and W6 and W7
have been filling it.

Hold out a set now, before optimising, and never optimise against it:

```bash
uv run python -m friday.skills.metrics --split --holdout 0.25 --out /srv/friday/eval/skills/
```

### 2. DSPy optimisation

Spec section 6's command, verbatim:

```bash
jarvis optimize skills --policy dspy
```

`# VERIFY:` the flags for scoping a run against OpenJarvis's own documentation. What matters
is the discipline around it, which is ours:

**One skill at a time, or one coherent group.** A run that touches twenty skills produces one
number you cannot attribute.

**Against the training split, evaluated on the holdout.** An optimiser scored on the examples
it optimised against reports improvement that does not exist. This is the single most common
way a skill-optimisation loop produces confident nonsense.

**Every run is a branch.** Spec section 9: branch only, human merge, not once and not for
small things. An optimised prompt is a code change.

```bash
sudo -u friday git -C /srv/friday/agent log --oneline -5
uv run python -m friday.skills.evaluate --skill morning_digest --split holdout --before-after
```

Then read the number and act on it honestly:

```
improved on holdout  ->  merge the branch, record before/after in the skill's own file
no change            ->  discard. Not "keep it, it might help later"
worse                ->  discard, and record what was tried so it is not retried in March
```

Done-when 3 is that a rejection has actually happened. An optimisation process with a 100%
acceptance rate is a process that is measuring its own output.

### 3. What she may and may not optimise

This is the week ADR-0004 earns its place, so state the boundary plainly before running
anything unattended:

```
she may write:    agent/skills/  agent/tools/  agent/prompts/  configs she owns
she may not write: agent/core/
```

Filesystem permissions, not instructions. The `friday` user cannot write `agent/core/`; the
`fridaysup` user owns it; the supervisor re-checks every 30 seconds and hard-stops on any
change. A process that can rewrite its own orchestration has no fixed point — every safety
property becomes a property of whatever it last wrote about itself.

Verify it again this week, because this is the first week she is actively writing code:

```bash
sudo -u friday test -w /srv/friday/agent/core && echo "BROKEN" || echo "ok"
sudo -u friday touch /srv/friday/agent/core/probe 2>&1 | tail -1   # must be Permission denied
sudo -u friday test -w /srv/friday/agent/skills && echo "ok: skills writable" || echo "wrong"
```

### 4. The Curator

Spec section 8, verbatim, and it was set in W1:

```bash
hermes model set auxiliary.curator fast
```

A weekly job that does not need 27B. Strict JSON out; a parse failure is a failure, not a
retry freeform (`config/agents.yaml`, `curator`: `fast`, `memory_read` only, `can_write:
false`, 8000 tokens, temperature 0.2).

The Curator's job is subtraction:

- **merge** near-duplicate skills
- **retire** skills not invoked in 60 days
- **flag** skills whose correction rate is rising
- **propose** consolidation of the vault where notes have fragmented

`can_write: false` is deliberate. The Curator proposes; you approve. The same rule as
Honcho's profile proposals in `config/memory.yaml` (`auto_apply_proposals: false`), and for
the same reason: a system that prunes itself unattended eventually prunes the thing you
needed.

```bash
sudo systemctl enable --now friday-curator.timer
uv run python -m friday.loops.curator --once --dry-run
uv run python -m friday.cli inbox --kind curator
```

Done-when 5 is that skill count has gone down at least once. If the library only ever grows,
the Curator is proposing and you are not approving, which is the same as not having one.

### 5. Steady state

Week 8 does not end. What the ongoing rhythm looks like:

**Weekly.** Curator run and review. Correction report from `scrutiny.db`. `make eval`. Skim
the digests for confident wrongness.

**Monthly.** `make backup`, and restore it somewhere to check that it restores — an untested
backup is a belief. Re-read the correction report as a whole for patterns rather than
incidents. Check bridge health; spec section 10 says re-link every few months, WhatsApp
especially. Check the corpus size against `max_live_events` and whether consolidation is
keeping up.

**Quarterly.** Re-read spec section 3 before installing anything, and ADR-0001 before adding
anything that overlaps a layer. Re-verify every license in the stack table — projects
relicense, and the AGPL and PolyForm rows are the ones to watch. Add eval questions from the
quarter's real failures. Re-check `agent/core/` ownership after any package upgrade or
careless `chown -R`.

**When something breaks at 3am.** `make preflight` first, then Langfuse, then the supervisor
journal. That order, because preflight is fast and reads everything, and because you
installed Langfuse in week 1 for exactly this moment.

### 6. Close

```bash
make preflight
make test
make eval
make known-good
```


```bash

sqlite3 /srv/friday/db/skills.db "select min(ts), max(ts), count(*) from invocations;"

# 2. Before and after are recorded per optimised skill, on the holdout.
uv run python -m friday.skills.evaluate --report --all

# 5. The core boundary held through a week of her writing code. ADR-0004.
sudo -u friday test -w /srv/friday/agent/core && echo "BROKEN" || echo "ok"
journalctl -u friday-supervisor.service --since '7 days ago' | grep -i 'core' | head

# 6. Retrieval did not move. Skill changes must not touch the eval.
uv run python eval/report.py --last 4

# 7. known-good only ever advanced after an eval pass. ADR-0009.
git log --oneline --decorate | grep known-good
```

## Failure modes

**Skill count is the metric.** The failure this week is named after. Four hundred skills, no
idea whether any of them got better. Success rate, correction rate, cost per success,
invocation count — and none of those is a count of skills.

**Optimised and evaluated on the same examples.** Reports improvement that does not exist,
and it is very convincing. Hold out a set before the first run and never look at it during
optimisation.

**Nothing is ever rejected.** You are measuring your own output. Check whether the holdout is
genuinely held out, and whether the metric can express a regression at all.

**The optimiser rewrote something it should not have.** Contained by ADR-0004 rather than
detected by review — she cannot write `agent/core/`, and the supervisor hard-stops if
anything does. If you find yourself wanting to relax that so an optimiser can "improve the
loop", that is the exact request the boundary exists to refuse.

**The Curator retires a skill you needed.** `can_write: false`; it proposes and you approve.
If it is applying changes directly, that is a config drift and it is a real one.

**Correction rate is not being recorded** because W6 and W7's ledger was treated as a
development aid. It is the only metric that measures whether output was right rather than
whether it completed, and without it "success rate" measures completion.

**The eval moved after a skill optimisation.** A skill reached into retrieval. They are
separate layers and the eval is the gate that noticed — this is the eval suite doing its job,
so revert the skill rather than adjusting the eval.

**Retrieval collapse arrives around 10k documents.** Spec section 10 predicted it and week 3
built the two things that save you: the reranker and the consolidation loop. If it is
happening anyway, check whether consolidation is actually running when full, or whether it
was quietly turned into a nightly job at some point (ADR-0007).

**A new project appears that does 60% of a layer better.** Spec section 3 and ADR-0001. Either
the feature belongs in the incumbent, or the incumbent is wrong and should be replaced. "I
need one feature from project X" is not sufficient grounds, and the answer is an ADR, not an
install.

## Do not do yet

There is no next week, so this section is what to keep not doing:

- **Do not let her write `agent/core/`.** Not for an optimiser, not temporarily, not with a
  comment explaining why it is safe this time.
- **Do not remove the `ask` boundary.** No timeout, no auto-approve, no "she was right the
  last twenty times."
- **Do not run an unbounded overnight task.** The budgets are the reason week 7's nights are
  uneventful.
- **Do not merge an agent branch unread.** Not once, not for small things.
- **Do not add a second owner for any layer.** ADR-0001, and it happens gradually: nobody
  decides to run two agent runtimes.
- **Do not skip the eval before advancing `known-good`.** ADR-0009 — it is what keeps
  "last-known-good" from meaning "last thing that started".
- **Do not stop logging corrections.** It is the fine-tuning set, and it is only valuable
  because it is unbroken.
