# Week 2 — the eval set, the calendar, and the first two senses

Spec section 6, week 2:

> Radicale + DAVx5; ingest Matrix db + calendar — she answers "what's my week look like"

And the instruction that governs the order inside this week, spec section 7:

> **Build the eval set before the ingestion.**

## Goal

Two things, and the order between them is the point.

First, write twenty-five questions about your own life with known answers. This is the least
interesting hour in the project. It is also the hour that decides whether she feels like
FRIDAY or like a chatbot with a filing cabinet, because it is the only artefact that can tell
you whether a retrieval change helped. Written after ingestion, the questions are quietly
shaped by what you already know is in the index, and they stop being a test.

Second, get calendar and messages flowing into a landing table, resolve dates in code, and
answer one question correctly: what does my week look like.

## Done when

1. `eval/questions.yaml` has 25 questions with known answers, written by you, none of them
   copied from `eval/questions.example.yaml`.
2. Radicale serves CalDAV on `127.0.0.1:5232`, DAVx5 on your phone syncs to it over the mesh,
   and an event created on the phone appears in Radicale's storage within a minute.
3. `friday-ingest-caldav.timer` and `friday-ingest-matrix.timer` are running, and
   `sources.db` grows.
4. Recurring events are stored as concrete occurrences, not as RRULEs.
5. Every ingested row carries a source, a timestamp, a sensitivity class, and an untrusted
   marker.
6. She answers "what's my week look like" correctly, including a recurring event and an event
   that moved.
7. Ask her the same question at 23:50 and the answer is still right. Temporal reasoning is
   resolved in Python, not by the model.

## Prerequisites

- W1 complete and `make preflight` clean.
- The mesh is up, because DAVx5 reaches Radicale over it. Spec section 9: no port forward,
  and a CalDAV server on the public internet with basic auth is the worst version of this.
- At least one mautrix bridge linked and backfilled, so `sources.db` has something to hold.

Preflight will still `FAIL` on Qdrant, which is week 3. That is expected.

## Steps

### 1. The eval set. First. Before anything below it.

```bash
cp eval/questions.example.yaml eval/questions.yaml
${EDITOR:-nano} eval/questions.yaml
```

`eval/questions.yaml` is gitignored. It contains your life; it does not belong in a
repository, even a private one.

Twenty-five questions. The pass mark is 20 (spec section 6). What makes a question useful:

- **It has one known answer** that you can write down now, and that will not drift.
- **It is about you**, not about the world. "What is the capital of France" tests the model.
  "What did I tell Sam I would do about the roof" tests retrieval, which is the thing that
  actually breaks.
- **The answer lives in a specific place** you can name. If you cannot say which source
  should have it, the question tests ingestion coverage rather than retrieval quality, and
  it will fail for a reason you cannot fix.

Spread them deliberately, because a set that is all one shape hides the failure that
matters:

| Shape | How many | Why it is in the set |
|---|---|---|
| Direct recall from one note | 6 | The baseline. If these fail, nothing else matters |
| Requires joining two sources | 5 | Where hybrid retrieval earns its keep |
| Temporal — "last month", "before the trip" | 5 | Spec section 10 names this as a breakage |
| About a person | 4 | Tests `people/` and pronoun resolution across notes |
| Negative — the answer is "you never told me" | 3 | The only questions that catch confabulation |
| Stale — true in March, false now | 2 | Tests provenance, spec section 7 |

The negative questions are the ones people leave out and the ones that catch the failure you
care about. A retrieval system that scores 25/25 by inventing three answers is worse than one
that scores 20/25 and says it does not know.

Write the answers with enough specificity to grade automatically but not so much that
phrasing counts as wrong. `expect_contains` on a distinctive string, not exact-match on a
sentence.

Do not run it yet. There is nothing indexed, so it will score zero, and that is correct.

### 2. Radicale

```bash
sudo pacman -S --needed --noconfirm radicale python-passlib python-bcrypt
sudo install -d -m 0750 -o friday -g friday /srv/friday/db/radicale
```

```bash
sudo install -d -m 0755 /etc/friday
sudo tee /etc/friday/radicale.conf > /dev/null <<'EOF'
[server]
# Spec section 9: no port forwarding. The phone reaches this over the mesh.
hosts = 127.0.0.1:5232

[auth]
type = htpasswd
htpasswd_filename = /etc/friday/radicale.users
htpasswd_encryption = bcrypt

[storage]
filesystem_folder = /srv/friday/db/radicale
EOF
```

The htpasswd write below is idempotent because `-B` on an existing file with the same user
replaces that user's line rather than appending a duplicate.

```bash
sudo htpasswd -B -c /etc/friday/radicale.users ak   # drop -c after the first user
sudo chown root:friday /etc/friday/radicale.users && sudo chmod 0640 /etc/friday/radicale.users
sudo systemctl enable --now radicale.service
curl -su ak http://127.0.0.1:5232/ -o /dev/null -w '%{http_code}\n'
```

Create two collections, `personal` and `work`, matching `config/sources.yaml`. Radicale
creates them on first write from a client, so the simplest path is to add both accounts in
DAVx5 and let it.

The Radicale password is a credential the ingest process needs. It goes in sops, and reaches
the unit as an environment variable named in `config/sources.yaml` (`RADICALE_USER`,
`RADICALE_PASSWORD`) — by name, never by value. ADR-0005.

```bash
sudo sh -c 'umask 077; printf "RADICALE_USER=ak\nRADICALE_PASSWORD=%s\n" "$(read -rsp "password: " p; echo "$p")" > /tmp/rad.env'
sudo sh -c 'SOPS_AGE_KEY_FILE=/srv/friday/secrets/age.key sops --encrypt /tmp/rad.env > /srv/friday/secrets/radicale.env.sops'
sudo shred -u /tmp/rad.env
```

### 3. DAVx5

On the phone, over the mesh: base URL `http://<mesh-ip>:5232/`, your Radicale username and
password. Sync both collections. Then create an event on the phone and confirm it lands:

```bash
sudo find /srv/friday/db/radicale -name '*.ics' -newermt '-5 minutes' | head
```

If nothing appears, the problem is the mesh or Radicale's `hosts` binding, not DAVx5.
Confirm the phone can reach 5232 at all before touching the client.

### 4. The ingest framework

Everything ingested is untrusted input. Spec section 9, and ADR-0006: tag it, and then put
the real boundary somewhere that survives the tagging failing. In week 2 the boundary is
that nothing ingested reaches a model with tools attached — the only consumer is retrieval,
and the scorer that will eventually read it has `tools: []`.

Write `friday/ingest/base.py` first, before either source. It owns:

- the `Source` protocol: `poll() -> Iterable[Event]`, nothing else
- the `Event` model — `source`, `external_id`, `occurred_at`, `body`, `sensitivity`,
  `untrusted`, `raw`
- idempotent upsert into `sources.db`, keyed on `(source, external_id)`, so a re-poll after a
  crash does not duplicate
- the untrusted wrap applied on write, in one place, so no source can forget it
- `max_events_per_poll` from `config/sources.yaml`, because after downtime a source has a
  backlog and an uncapped first poll floods everything downstream

Sensitivity is assigned at ingestion and is not optional. ADR-0008: a source without a class
is a bug. `matrix` and `notmuch` are `messages`, files under the vault are `vault`, calendar
is `any`.

```bash
uv run python -m friday.ingest.base --init-db
sqlite3 /srv/friday/db/sources.db '.schema events'
```

### 5. Calendar ingest

`friday/ingest/caldav.py`. The one thing that must not be deferred: expand recurrences into
concrete occurrences. A retrieval index cannot match "Thursday" against an RRULE, and this
week's entire test is a question about a week.

```bash
uv run python -m friday.ingest.caldav --once --dry-run | head -n 20
uv run python -m friday.ingest.caldav --once
sqlite3 /srv/friday/db/sources.db \
  "select count(*), min(occurred_at), max(occurred_at) from events where source='caldav';"
```

`backfill_days: 365` and `horizon_days: 90` are in `config/sources.yaml`. The backfill is a
one-time cost and it is what makes "what did we decide at that meeting in April" answerable
in week 3.

Moved and cancelled events are the interesting case. An occurrence that shifts must update
in place rather than appearing twice, which is what the `(source, external_id)` key is for —
and for a recurring series, `external_id` must include the occurrence date or every
occurrence collapses onto one row.

### 6. Matrix ingest

`friday/ingest/matrix.py`. Read Conduit's own database, not the client-server API — Hermes
already holds a sync token, and two consumers sharing one means one of them silently misses
messages. `config/sources.yaml` says this and it is the reason.

```bash
uv run python -m friday.ingest.matrix --once
sqlite3 /srv/friday/db/sources.db \
  "select room, count(*) from events where source='matrix' group by room order by 2 desc limit 10;"
```

Bridged rooms carry other people's words. They are `sensitivity: messages`, they pin local
by ADR-0008, and they are the highest-risk untrusted input in the system until mail arrives
in week 4.

Copy the database before reading it if Conduit holds a write lock; do not open its live file
read-write under any circumstance.

### 7. Timers

```bash
sudo bash install/04-services.sh
sudo systemctl enable --now friday-ingest-caldav.timer friday-ingest-matrix.timer
systemctl list-timers 'friday-ingest-*' --no-pager
```

Intervals come from `config/sources.yaml`: 15s for Matrix, 300s for CalDAV. A timer, not a
daemon, so a wedged poll cannot silently stop polling forever — systemd restarts it on the
next tick and the failure is visible in `systemctl list-timers`.

### 8. Temporal resolution, in code

Spec section 7: "Always inject current date/time and today's calendar; local models are
hopeless at temporal reasoning otherwise." Spec section 10 says it again from the other side:
"Resolve dates in code, never in the prompt."

`friday/temporal.py` owns every conversion between a phrase and a date range: "this week",
"next Tuesday", "before the trip", "last month". The model receives resolved ISO ranges and
never performs date arithmetic.

```bash
uv run pytest tests/test_temporal.py -q
```

Test it at the boundaries, because that is where it fails and where you will not notice: at
23:50, on a Sunday, across a month end, across a DST change, and with `timezone` in
`config/friday.toml` set to something other than UTC. Set it now if you have not:

```bash
grep timezone config/friday.toml
```

A wrong timezone makes every calendar answer wrong in a way that looks like a retrieval
problem for about two days.

### 9. The question

```bash
uv run python -m friday.cli ask "what's my week look like"
```

Injected before retrieval, always: the current date and time, and today's calendar. Not
retrieved — injected. Retrieval can miss; the date cannot be allowed to.

## Failure modes

**The eval questions were written after ingestion.** Not detectable by any command, and it
quietly removes the value of the whole set: you unconsciously ask what you know is in there.
If this happened, the honest fix is to write ten more questions before you look at the index
again.

**Every recurring event lands on one row.** `external_id` is the series UID and does not
include the occurrence date. Every weekly standup collapses onto whichever occurrence was
polled last, and "what's my week look like" returns one meeting.

**Timezone drift.** Radicale stores UTC, the phone sends local, `config/friday.toml` says
UTC because nobody changed it. Everything is subtly wrong by a fixed offset, which reads as a
retrieval problem. Check the timezone before you debug retrieval, this week and every week.

**Matrix ingestion misses messages.** Two consumers sharing one sync token. Read the Conduit
database as `config/sources.yaml` specifies. If you took the client-server API shortcut, this
is the failure, and it is intermittent, which makes it expensive.

**Conduit database locked.** `sqlite3.OperationalError: database is locked` in the ingest
log. Copy before reading. Never open it read-write.

**The first poll after downtime floods.** `max_events_per_poll: 500` exists for this. If you
removed it because it seemed arbitrary, a bridge backfill of six months arrives in one poll.

**DAVx5 syncs but the box has nothing.** Radicale bound to `0.0.0.0` and the phone talked to
a different address than the one you are looking at, or `hosts` is right and the phone is off
the mesh. `ss -tlnp | grep 5232` answers this in one line.

## Do not do yet

- **No Qdrant, no embeddings, no FTS5.** Week 3. `sources.db` is a landing zone and not the
  index; `config/sources.yaml` keeps it for 30 days and the episodic log is the durable
  record.
- **No consolidation loop.** Nothing writes to the vault yet except you. Week 3.
- **No mail, no files, no browser, no Home Assistant.** Week 4, one at a time, with the eval
  re-run between each. `config/sources.yaml` has them all `enabled: false` and marked `week: 4`.
- **No voice.** Still. The microphone is week 4 at the earliest.
- **Do not tune retrieval.** There is no retrieval. If you find yourself adjusting
  `min_rerank_score` this week, you are in the wrong file.
- **Do not run the eval to see where you are.** It scores zero. Running it now teaches you
  nothing and trains you to ignore a red result.
